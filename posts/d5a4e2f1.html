一、起因：红字不是那天才有的

先把一个容易被误会的说法纠正掉：这不是「某天随手按了下 F12，才发现控制台红了一片」的故事。

这些报错我早就知道。

三四年跑下来，站里依赖的那些外部资源是一件一件慢慢死掉的。它们很守规矩，从来不一起罢工：某段时间是某个 CDN 开始抽风，过一阵换成某个图床连不上，再往后是某个公共接口悄悄停了服。死一个，页面上就少一样东西 —— 某个图标不显示、某张图变成裂图、某个小模块空着。文章照样能读，页面照样能开。

我也不是没看见。F12 按过很多次，每次都想「下次一起修」，然后下次又变成了下次。坏掉的东西只要不影响你看文章，就永远排在待办清单的最后一条。

真正让我下决心的是发现死掉的东西已经从边角蔓延到了骨架。那天我本来只是想看看某个 CSS 改动的效果，随手按了下 F12，看到的就是这些：

二、第一轮：先把「哪些东西真的死了」搞清楚

修之前得先知道坏了多少。

这里有个坑值得单独说：光看浏览器报错是不够的。浏览器只会告诉你「我这次没拿到」，但不会告诉你「这东西是不是早就没人维护了」。有些 CDN 你本地挂了是因为你自己的网络，有些是真死了。

所以第一件事是挨个探测：把首页要加载的第三方资源全列出来，逐个发请求，看状态码、看响应字节、看首字节时间。

8.1 先抓到的不是背景，是 Service Worker

控制台里最扎眼的是这几条：

`@
Uncaught (in promise) TypeError: Failed to convert value to ‘Response’. sw.js:1

Fetch error: http://localhost:4000/css/index.css
TypeError: Failed to convert value to ‘Response’.
at handle (sw.js:197:16)
at sw.js:15:27
`@

Failed to convert value to 'Response' 是个很好认的症状：respondWith() 收到了一个 undefined。

问题出在 themes/butterfly/source/sw.js（现已改名为 themes/fomalhaut/） —— 这是早年从别处抄来的一个「CDN 分流器」，作用是把静态资源转到对象存储去取。要命的是这一段：

@js return fetch(req).catch(error => { console.error('Fetch error:', req.url, error); }); @

catch 回调里少了一个 return。请求成功时看不出来，一旦失败这个函数就返回 undefined，紧接着 event.respondWith(undefined) 直接抛错，这个请求当场作废。

更糟的是它给所有同源请求都套了 respondWith（文件里甚至注册了两个 fetch 监听器，第二个是半成品，里面用了一个从未定义过的变量）。也就是说：那一跳只要失败，CSS、图片、脚本就可能整片加载不出来。

「背景图没了」其实只是它的连带伤害之一。

修法没什么玄学：

  • 只拦截目标域名（www.fomal.cc）的 GET 请求，其余请求直接 return，根本不调用 respondWith；
  • 分流失败先回退 return await fetch(req)，再失败才返回 504 兜底；
  • 本地开发环境（localhost / 127.0.0.1）自动注销 Service Worker，免得调试时一直被缓存的版本阴。

Service Worker 真正的坑在于它是「隐形」的：注册过一次就会一直活着。哪怕你把源码删了、把注册代码去掉了，老访客的浏览器里那个旧版本还在拦截请求 —— 你改了文件，他看到的还是老逻辑。

所以改完 sw.js 之后，记得去 Application → Service Workers 里确认新版本已经接管，必要时手动 unregister 再清一下 Cache Storage。

8.3 真正的元凶：7 个随机壁纸 API 死了 5 个

那 JS 为什么写不出有效的背景？因为美化模块允许自定义背景，地址存在 localStorage.blogbg 里。顺着这个值往下查，挖出两个坑。

坑一：一个拼错的单词。

「恢复默认背景」按钮的代码是这样的：

@js function resetBg() { localStorage.setItem("blogbg", "deafult"); // default 拼成了 deafult resetBg_(); } @

只要点过一次，这个非法值就永久留在浏览器里：之后每次加载，判断 blogbg == 'default' 都是假，于是走自定义分支，把 --default-bg: deafult; 写进 CSS —— 一个非法值，浏览器直接忽略，背景全空。

十二、给页脚加了个「旅行者 1 号」

页脚那个计时器（「本站居然运行了 X 天 X 小时 X 分 X 秒」，白天挂「科研摸鱼中」的牌子、晚上换成「下班休息啦」）跑了两年多，这次在旁边加了一句更远的东西：

旅行者 1 号当前距离地球 25,0xx,xxx,xxx 千米，约为 1xx.xxxxxx 个天文单位（信号单程需 XX 小时 XX 分）🚀

这东西不能随便算。「距离 = 速度 × 时间」那种近似公式，放到两百多亿公里外误差能到几百万公里。所以做法是从 JPL Horizons 取真实星历（DE440 地球星历 + Jacobson 2022 的旅行者 1 号解），离线做最小二乘拟合，把系数直接打进 fomal.js，运行时只做多项式求值——不联网、不请求接口，也不会哪天因为第三方接口停服而变成空白（这个教训前面刚吃过）。

模型拆成两块：

  • 旅行者 1 号：线性趋势 + 切比雪夫残差（3 个坐标 × 47 项）
  • 地球：年谐波（含线性慢调制）+ 月球项（3 个坐标 × 26 项）

在日心黄道 J2000 坐标下分别算出两体位置，再取几何距离 |r_V1 − r_earth|。时间也要处理：系数是按 TDB 儒略日拟合的，输入毫秒时间戳得先换算 jd = ms / 86400000 + 2440587.5 + 69.184 / 86400（那里多出来的 69.184 秒，是从 UTC 到 TDB 的近似差）。

有效期 2026-01-01 ~ 2100-01-01，窗口外自动钳位到边界（退化成只保留线性趋势），不会算出离谱的数。精度上，与 Horizons 的几何距离对着比（2026—2100 年两万多个独立采样点）均方根约 4000 千米、最大约 12000 千米（≈ 8×10⁻⁵ 天文单位）——已经远好于 JPL 自己对旅行者 1 号位置的预测不确定度（2030 年约 ±20 万千米）。

还有个细节值得单独说：它输出的是几何距离（此刻真实距离），不是光行时修正后的视距离；旁边那句「信号单程需 X 小时 Y 分」就是拿这个距离除光速再取整。

十四、把「刷新时先闪一下」也抹平了

前面背景图修好之后，我注意到一个更细的毛病：每次刷新页面，会先闪一帧默认壁纸（还有默认字体），然后才跳成我自己设的那张。

不算故障，但很扎眼。原因也不复杂：壁纸、卡片透明度、主题色这些美化设置都存在 localStorage 里，而负责读它们、再把值写进 CSS 变量的那 3800 行 fomal.js，是放在页面底部、等 HTML 和 CSS 都处理完才开始跑的。第一帧渲染时，CSS 用的还是 :root 里的默认值——于是先画一帧默认壁纸，再被脚本改掉。

要抹掉这一帧只有一条路：赶在首帧之前把值写进去。于是在 _config.fomalhaut.yml 的 inject.head 里插了一段内联脚本（<script id="beautyBoot">）：它同步执行，早于 body 解析、也早于首帧。位置很讲究——必须放在那批 <style id="..."> 标签后面，否则 document.getElementById() 什么都拿不到。

它一共接管八类设置，套路都一样：读 localStorage，然后直接改对应 <style> 标签的 textContent：

  • 自定义壁纸 → defineBg
  • 卡片透明度 → transPercent
  • 背景滤镜（模糊 / 饱和度 / 对比度）→ bgFilterParam
  • 主题色 → themeColor
  • 字体 → --global-font（选「默认字体」时，还要像 fomal.js 那样动态插一段 <style>）
  • 侧边部件 / 侧栏显隐 / 侧栏位置 / 顶栏常驻 / 霓虹灯 / 帧率开关 → rightSide、aside-show、aside-pos、nav-display、menu_shadow、#fps

几个必须对齐的细节：

  1. 壁纸要连 --darkmode-bg 一起写（脚本里那个 SAME = ";--darkmode-bg:" 常量就是干这个的），不然切到夜间模式还是旧图；
  2. 取值规则必须和 fomal.js 的初始化逐字一致：null、空串、字符串 "undefined" / "null" 都算「没设置」，走默认值；
  3. 这段脚本只是提前把同样的值写一遍，不新增任何请求，也不改 fomal.js 的逻辑——两边的结果必须一模一样，否则会出现「刷新后闪回默认值」这种更诡异的现象。

写的时候先在 .tmp-boot-draft.js 里当独立文件调通，再内联进配置。要说这轮修的东西里哪些最不容易被发现，就是这种「一帧」级别的问题：它不影响任何功能，只在每次刷新的头 100 毫秒里出现一次。

十五、美化面板里那根「点不动」的滑条

顺手修的第二个体验问题：卡片透明度那根进度条，只有拖右边那个圆点才有反应，点轨道左边完全没动静。

两个原因叠在一起：

  • input[type=range] 本体只有 5px 高，圆点却有 15px——想点中那 5px 的细线本来就很难；
  • 更麻烦的是它上面盖了一层 .rang_width（position: absolute）用来显示彩色进度，这层把鼠标事件全吃掉了，点下去根本传不到 input。

修法分三层，缺一层都不成立。

一、把可点击区域做大（custom.css）：.range 加 padding: 9px 0，视觉高度不变，可点区域从 5px 扩到 23px；顺手加 cursor: pointer、user-select: none，触屏上给 touch-action: pan-y——纵向照样滚页面，只有横向拖动才交给滑条。

二、让进度条别再挡路：.rang_width 的 top 跟着 padding 对齐到 9px，并加 pointer-events: none。它只是装饰，不该接收事件。

三、坐标换算（fomal.js 里新写的 rangeValueFromX()）：把鼠标横坐标换成滑条的值。这里有几个容易算错的地方：

  • 要扣掉圆点自身的宽度（usable = rect.width - 15），否则拖到最右边永远到不了 max，最左边也点不出 min；

二十三、美化面板里那面错排的图墙，和那个不像控件的取色框

原因在两条 CSS 上：

  • custom.css:1120：.pimgbox, .imgbox, .box { height: 100px; width: 166px; margin: 10px; }（≤768px 时宽度改成 135px、高度 73px）

第二个是那个取色框。 「四、背景设置 → 5. 纯色」里的取色框一直是浏览器原生外观：比旁边的色块高 10px（110 对 100）、方角、多一圈 1px 边框，一眼就能看出「这不是同一个世界的控件」。改法是：

三十一、美化面板的初始尺寸不再靠猜

四十四、又是两个「静默失效」的 bug

二是首页轮播「有时候图片出不来」。 具体是站内跳转回首页（pjax 往返）之后，轮播绕回那一下图片区域是空的，直接刷新首页反而正常 —— 所以是「有时候」。链条捋下来是三方时序问题：主题开了懒加载，图片 src 被换成占位图、真图放在 data-lazy-src，靠 main.js 里一个 LazyLoad 实例在登记的时候填回去；pjax 完成时主题先重新执行一遍轮播脚本（新建 Swiper），紧接着同步调了一次 lazyLoadInstance.update() —— 而 Swiper 的循环克隆 swiper-slide-duplicate 是在构造之后才插进 DOM 的，克隆永远晚于那次 update，于是循环到克隆位就没图。修法是在页面加载完成、pjax 完成、以及 MutationObserver 观察到轮播 DOM 变化之后，各补一次 update()。刷新不复现的原因也清楚了：正常加载时 defer 脚本先跑，LazyLoad 构造时克隆已经在 DOM 里。

六十五、星空关了它还在画，玻璃效果只留给桌面端

两处性能问题的根子都是「不管有没有用，先算着」。

第一处：星空特效。 用美化设置把星空关掉（settings.js 把 #universe 的 style.display 改成 none）之后，暗色模式下那个 canvas 动画循环依然每帧重绘整页画布 —— 循环里只看 data-theme 是不是 dark，从不看画布到底有没有在显示。effects.js:184 起加了一层可见性判断：starOn 缓存结果，用 window.getComputedStyle(s).display 取真实显示状态。

判定不能用 offsetParent —— #universe 是 position: fixed，它的 offsetParent 恒为 null，用它判断会永远认为「不可见」。缓存失效靠两个 MutationObserver（一个是 documentElement 的 data-theme / class / style，一个是画布自己的 style）加 resize 和 pjax:complete，另外每 45 帧（约 0.75 秒）再强制复核一次兜底 —— 宁可多算一帧，也不能出现「星空冻住不动」。

第二处：侧栏个人卡的磨砂玻璃。 backdrop-filter: blur(11px) saturate(1.45) 这种效果，弱 GPU 上滚动时是逐帧重算背景的。现在它只在 @media (min-width: 1200px) 的桌面端启用，窄屏与平板降级成实底半透明面板 —— 卡片还是卡片，只是不再实时模糊。

六十七、搜索框的 88 KB，不该每一页都付

主题原来在每一页都输出 Algolia 三连，而且三个都没有 defer：

  • algoliasearch-lite.umd.js 13.6 KB（压缩后约 4 KB）
  • instantsearch.production.min.js 277 KB（压缩后约 88 KB）
  • /js/search/algolia.js 5 KB

合计 296 KB，压缩后约 88 KB，全站每页都付一次下载加解析 —— 而它们只有在用户点开搜索框之后才用得上。

新方案分两段，做在 source/js/inject/search-lazy.js（221 行）里：

  1. 空闲预取：页面 load 之后的空闲时刻，用 <link rel=prefetch> 把三个文件静静拉进浏览器 HTTP 缓存。只下载、不执行 —— 不占主线程，也不和首屏图片抢带宽。
  2. 点击兜底：万一用户点得比预取快，先把搜索面板立刻打开（有反馈，不像卡住），再按顺序注入三个脚本，就绪后自动聚焦输入框。最差等于原来的体验，最好等于零等待。

地址不写死：additional-js.pug 里原来那三条 <script> 换成一行 window.__SEARCH_LAZY__ = […]（URL 仍由主题的 CDN 配置解析出来），运行期只消费它 —— 以后换 CDN 只改配置。

这中间埋着一个必须绕过的坑：主题的 algolia.js 整段包在 window.addEventListener('load', …) 里。页面已经 load 过之后，load 不会再来第二次 —— 直接把脚本注入进去，整个搜索模块永远不会初始化。所以脚本在「readyState 已是 complete」时，执行 algolia.js 期间临时接管 window.addEventListener，把注册进来的 load 回调当场同步执行，脚本一跑完立刻还原。另外 #search-button 在 #body-wrap 里、会被 pjax 换掉，所以点击用 document 捕获阶段委托；而搜索面板和遮罩在 #body-wrap 之外，换页后状态还能保留。

六十九、鼠标上那次闪出来的 I 形光标

这个 bug 挺难描述：鼠标停在某些文字上时，会偶尔闪出一个 I 形（文本选择）光标，而旁边那圈粉色的自定义圆点一直正常。

根因在 source/js/modules/cursor.js。create() 干两件事：先遍历全页元素、用 getComputedStyle 收集所有 cursor: pointer 的元素；之后才往页面里 append 一条通配样式，把系统光标全部替换掉。而 refresh() 的第一句是 this.scr.remove() —— 于是「删样式 → 全页重新扫描 → 重新 append」之间有一个空窗，几十毫秒里浏览器退回了 auto，停在文字上就是 I 形光标；那圈粉色圆点是 DOM 元素，不受影响，所以看起来只是「光标闪了一下」。

空窗有多长量过：关于页 3030 个元素，refresh() 全程 37.5ms。而这个函数不只换主题色时会被调 —— settings.js:205 每次页面加载都会调一次 setColor()，所以每次刷新都会闪一次。

改法只动 cursor.js 一个文件：create() 里把样式节点的挂载挪到扫描之前，并且只创建一次（if (!this.scr)），以后只改写它的内容；refresh() 删掉那句 this.scr.remove()，只重置悬停与坐标状态；主题色取值再加一层兜底 map.get(localStorage.getItem("themeColor")) || map.get("green")。

七十一、公告栏上多出来的一串 ms

公告栏里现在每条线路后面都挂着一小串数字：82ms。这是新增的 source/js/inject/ping-route.js（11.2 KB）加一个只管参数的 ping-route-boot.js。

浏览器里发不出 ICMP，所以这不是真的 ping：它用 fetch() 请求该线路域名根路径上一个带随机串的地址，然后取 Resource Timing 的 responseStart − startTime —— 也就是「发出请求 → 收到响应首字节」的时间，正好是一次 HTTP 往返。它包含 DNS / TCP / TLS，所以首轮数字会略高于稳态，但这恰好是「从本机打开这条线路要等多久」的真实感受值。

不拖慢页面的六条措施：全部在 window.load 之后用 requestIdleCallback 才开跑；四条线路错开 180ms 依次探测（第一个再等 350ms）；单次 8 秒超时（AbortController）；失败 1.5 秒后重试，封顶两次；请求走 no-cors 加随机查询串，不读响应体也不解析，命中不了站点的 SW 缓存；同一时刻只允许一波探测（busy 闸），pjax 换页后重建。

样式在 site-inject.css 的公告卡块里，徽标状态分五档：等待 / 加载 → ok（主题色）、slow（≥400ms，琥珀）、bad（≥1s，红）、fail（一条横杠加删除线）。徽标锁死 min-width: 42px，所以从「—」到「···」再到「82ms」，长度变化都不会把排版挤动。

这里还吃到一条用户实测反馈：一行里塞不下的时候，原来会把注记挤到第二行、把行撑高。现在 .a-row 一律 flex-wrap: nowrap —— 要么让注记自己省略成 Cloudfl…，要么由容器查询按宽度逐档收起注记和徽标，绝不换行。

七十七、两个只在线上才会犯的错

这一整天最难查的两个 bug，共同点是：本地完全正常，只有线上（或者只有手机上）才出问题。

第一个：朋友圈线上只剩空白卡片。 那页的内联注释里写了一句「本注释内禁止出现带尖括号的 style / script 标签名」，就是这次踩出来的教训。原因在 gulp：gulp-htmlclean 压缩 HTML 时，会把注释里的 <style> / <script> 标签名当成真的开始标签，于是页面里真实的那几个 style / script 区块和「注释里开出来的标签」互相嵌套、互相「保护」，还原失败之后整页正文被整段丢弃 —— 本地不跑 gulp，所以我怎么看都是好的，线上只剩一副空白卡片。

第二个：友人帐和八宝箱的分类标题图标在手机上被裁掉。 风车图标的负外边距是全局的 -1.35rem（约 21.6px），而窄屏下卡片左内边距只有 14px —— 兜不住，图标被顶出卡片、在手机视口里被裁。修法是给这两个页面的标题补回 1.6rem（大于 1.35rem），下划线也跟着文字一起右移。这两个页面是在同一分钟改完的，改动各 5 行。

七十八、先看看页面到底有没有闲着

上一轮把画布、模糊这些大头处理了，「静置时风扇还转」的问题却只解决了一半。于是把首页和文章页各打开、什么都不做，看浏览器到底还在忙什么。结论是：这个页面从来没有空闲的时候。

  • 四条常驻的 requestAnimationFrame 循环：星空、光标跟随、阅读进度、帧率计数器 —— 都不看有没有活干，一直往下递归。
  • 十四条 infinite 的 CSS 动画，其中十二条动的是 top / left / box-shadow：三个都不是合成属性，每帧都要重排加重绘。
  • onscroll 上的回调没有节流：触控板一次滑动会在一帧里发几十个 scroll 事件，每个事件都读六个布局值再写样式 —— 等于一帧里强制同步布局几十次，这是滚动顿挫的主因。

这一轮改动都做到「零观感变化」：

  • 阅读进度（reading.js）：percent() 原来直接挂在 window.onscroll 上，现在用 rAF 合流 —— 一帧最多算一次，并且只在百分比数字真的变了才写 DOM（原来每次 scroll 都要写一次 style 和 innerHTML）。__pctLast = -1 表示「还没写过」，与 0~94 都不冲突。
  • 帧率计数器（reading.js 的 startFps）：它自己就是一条常驻 rAF，在面板里把「帧率监测」关掉之后循环还在跑。加了 window.__fpsRunning 单例标记，关掉就不再启动，重新打开时补启动（避免叠加出两条循环）。
  • 光标跟随（cursor.js）：render() 原来每帧无条件 requestAnimationFrame 递归下去，鼠标不动也在写 #cursor 的 left / top。现在按「剩余距离」判停：缓动追上（< 0.1px）就退出循环，mousemove 或 refresh 再唤醒。阈值 0.1px 远低于视觉可辨，拖尾手感与原实现一致。
  • 主题色（settings.js）：setColor() 里那句 CURSOR.refresh() 会对全站元素做一次 getElementsByTagName('*') + getComputedStyle 扫描（3000+ 元素实测约 37ms），而启动时必然执行一次，此时光标模块刚用同一个 localStorage 值建过列表 —— 这一次扫描纯属白干。现在只有主题色真的换了才重扫。
  • 猫咪气泡（cursor.js）：mousemove 的 hover 判定同样合流到一帧一次。

八十、玻璃、呼吸灯和星星

上一节说过，作者卡的实时模糊只在 ≥1200px 启用，先把窄屏省了下来。这一轮想清楚一件事：滚动的那一半才是最贵的。

卡片本身随页面滚动，而它背后的 #web_bg 是 position: fixed 不动的 —— 于是浏览器每一帧都要对「卡片此刻盖住的那块背景」重做一次高斯模糊。干脆把桌面端那档也关掉：用同样特异性的选择器把 backdrop-filter 置 none（本文件在主题样式之后加载，后声明者胜）。渐变一个字没动，卡片的白色罩层、顶部渐隐、整体明度完全不变；唯一差别是卡片上半部分背后的背景图不再是磨砂的，而是清晰原图。文件里留了一段注释掉的备用方案：嫌背景图太花就取消注释，它会把渐变整体提白 8% 左右。

呼吸灯同理。 huxi_light / huxi_dark 动的是 box-shadow，每帧都要重绘；而它挂在头像上、永远在动。这一轮把它从 box-shadow 搬到合成层：关掉全站的 box-shadow 呼吸灯，改用头像外面两个静态光晕（一暗一亮）的 opacity 交叉淡入淡出 —— 浏览器只改合成参数、不重绘；时间轴（4s ease-in-out infinite）与颜色配方都不变。顺带压掉切换后露出来的静态白环。手机抽屉里那颗保留原来的 box-shadow 版本，但改成只在抽屉 .open（真的拉出来）时才呼吸；prefers-reduced-motion 那段也同步改写。

星星。 暗色星空的重绘从「跟着屏幕刷新率」限到 30fps：星星数约 0.216 × 视口宽（1440px 约 311 颗），每颗要 move / fadeIn / fadeOut / draw 各一次 beginPath + arc / rect + fill，流星还要再画 30 个矩形 —— 原来 60Hz 每秒画 60 次，144Hz 的屏幕每秒画 144 次。而星星本身漂得极慢（每帧 0.05~0.3px），30fps 与 60fps 肉眼分不出来。常量是 STAR_DRAW_INTERVAL，改成 0 就还原；初值取负无穷，保证切到暗色后第一帧立刻画，不用先等 33 毫秒。

八十一、gulp 把 @container 吃掉了

现象很小：本地 hexo server 看公告栏一切正常，部署之后「差一点」—— 按钮与「欢迎信息」之间少了一条间距。

八十二、资讯卡多了一格「更新」

侧栏小站资讯卡的时间条原来两项：已运行 / 距上次发文。现在多了第三格「更新」= 最近一次部署时间。

第一版想拿 GitHub API（产物仓库的最近一次提交）来算 —— 但那要吃不认证的 60 次/小时限流，为了侧栏卡的一个数字不值得。改成同源方案：

  1. 部署工作流在跑完 gulp 之后写一个 public/deploy.json，内容是本次构建时刻（UTC ISO8601）加 commit sha 与 run id。必须放在 gulp 之后 —— gulp 会处理 public/，写早了会被覆盖。
  2. 模板里的元素带两个属性：data-deploy-api（url_for 出来的 /deploy.json）与 data-deploy-build（本次构建时刻，先显示成 MM-DD）。
  3. 脚本读 deploy.json 换算成「刚刚 / N 分钟前 / N 小时前 / N 天前」，超过 30 天直接给日期；同源小文件随便读，结果还存 localStorage 十分钟，翻页不重复请求；带上 cache: 'no-store' 免得浏览器缓存把旧时间喂回来。
  4. 兜底优先级：读到真值 > 构建时刻 > 「—」；只接受更新的时间，绝不把时间往回退。失败时也记一个 lastTry，不让它一分钟一请求。
  5. 顺带一条不相干的兜底：计数服务（Vercount / 不蒜子）的 span 如果六秒后还是空的或还在转圈，一律写「—」，免得统计服务再挂一次时读者一直看 spinner。

有个小地方值得记：模板里那条注释还写着「用 GitHub 部署仓库的最近一次提交时间校正」——那是第一版的说明，当天就换掉了，注释没跟上。这种过期的注释最容易被下一个人当成真的。

八十四、最后说两句

回头看这次维修，我大概有这么几个感受。

第一，老站的问题往往是"你以为它在工作"。 MathJax 那个字段挂在配置文件里三年，主题从来没读过；Element-UI 拖着 905KB，实际只用了个 Toast；背景图那 4 个 CSS 变量干脆没有人定义过。这类问题不会报错，只会让你觉得"网站好像有点慢，但也能用"。

而且它们不是某天一起坏掉的，是一件一件慢慢失效的 —— 今天死个 CDN，下周死个图床，隔几个月死个接口。每次只坏一点点，每次都不影响你读文章，于是就永远轮不到修。等哪天真的攒够了，你会以为是"网站突然出问题了"，其实是三年的账单一起到期。

第二，判断性能不能只看单点。 换源之前我以为 CDN 就是瓶颈，结果一测发现我自己首页的 TTFB（693ms）比任何一个 CDN 都慢。省下来的那几百毫秒，可能还不如把 Vercel 的接入优化一下。做事要算总账。

八十八、不该跑的动画，就让它彻底停下来

雪花和星空这两块画布，10 月 4 日做过一轮性能修复：画布不可见就不画。这轮把它推进成了一步更狠的：不可见就退出循环。

区别在哪？原来判断为「不可见」之后，只是跳过了这一帧的绘制，requestAnimationFrame 仍然在每帧排下一帧，回到回调里先做一次 getComputedStyle、再走一个闭包调用。默认设置下雪花是关着的，也就是说这些开销全天候、纯白干。现在条件不满足直接 return，不再排下一帧，循环真正归零。

那怎么恢复呢？原来还有个「每 45 帧复核一次」的兜底轮询，这轮一并删了 —— 恢复完全交给失效回调：MutationObserver（盯 style / data-theme / class）、resize、pjax:complete，状态一变就重新问一次可见性，可见就把循环重新拉起来。雪花和星空现在用的是同一套套路，见 source/js/modules/effects.js:52-90 和 :222-258。

注释里专门留了两句话给以后的自己：雪花不要加降频，它的观感全靠 60fps，降帧一眼就能看出卡；星空本来就已经限到 30fps（STAR_DRAW_INTERVAL = 1000 / 30，星星漂得极慢，30 和 60 看不出差别），停 / 起循环都不改变这个间隔。

导航栏标题与右侧栏收放那个处理器，原来长这样：window.scrollCollect = () => { return btf.throttle(fn, 200)() }；回到顶部 / 目录定位那个也一样：window.tocScrollFn = function () { return btf.throttle(fn, 100)() }。看着像节流，其实浏览器每次滚动调用的是这个工厂函数：每次都要新建一个 throttle，再当场调用一次执行掉，然后把返回的空函数扔掉。结果就是节流形同虚设（滚动多快就执行多快，还白白给每个事件造一个定时器）。

现在两处都改成了直接把 btf.throttle(...) 的结果注册成监听器，200ms 和 100ms 才真正生效，而且节流状态能跨滚动事件保持。themes/fomalhaut/source/js/utils.js 里也给 btf.throttle 补了一个 cancel()：清掉定时器、清 context / args、把 previous 归零 —— 因为「删掉监听器」并不等于取消它已经排好的尾调用。

配套的生命周期也一起收拾了：scrollFn / scrollFnToDo 每次重新执行前，先把上一页的监听解绑、cancel()、置 null（它们并不只在 PJAX 换页时执行，所以不能只依赖 pjax 钩子）；themes/fomalhaut/layout/includes/third-party/pjax.pug 里那段手写的两句解绑换成了一个 forEach 循环，顺便把 '#bibi' 从 pjaxSelectors 里删掉 —— 那个文件早就删了。这个模块的版本号相应提到 ?v=20261005-scroll1。

九十二、动画的「生命周期」：小猫咪、滚动条与帧率

傍晚这轮全在收拾动画和监听的生命周期，四个模块，思路是同一条：读写分开、不做白工、停得掉。

小猫咪（source/js/modules/cursor.js，266+/251-）：高频的指针输入只记录最新值，统一到下一帧里先读完几何、再增量写入；写进去的值用 WeakMap 缓存起来（CSSOM 会把小数和单位规范化，拿序列化后的 style 反复比较是比不准的），值没变就一个字节都不碰 DOM；目标元素按需识别并缓存，不再每次全页遍历。注释里那句我留得很直白：「原地改样式，不移除；任何时候都不能露出文字区域的系统 I 形光标。」

手机端自绘滚动条（source/js/modules/shell.js，68+/23-）：滚动 / 布局值先在读阶段一次采完，节点创建和样式写入放到写阶段，避免读写交错引起多次重排；PJAX 有可能只替换掉轨道里的滑块，所以 ensure() 要同时校验 track 与 thumb 的父子关系，换了节点就以当前值为基准重新绑定缓存；桌面端必须在任何布局读取和节点创建之前就退出；可见性只在状态真的翻转时才改 class；滚动本身合并到一帧（schedule + frame 去重）。

美化面板（source/js/modules/settings.js）：Cursor.refresh 不再遍历全页元素，只有主题色真的变了才刷新光标；帧率面板改成「开着才起循环」—— 以前把开关关掉之后，采样循环还在后台一直跑。startFps / stopFps 成对出现，面板节点缺失也不影响取消采样和保存偏好（fpsPanel 提出来做了空值保护）。

九十五、补记：线上比本地卡，最后是广告拦截器干的

这轮的开头是一句听起来像玄学的话：同一个浏览器、同一个页面，本地 80-90fps，线上动一动鼠标就掉到四五十。

我一开始的怀疑方向有两个，都不对。

第一个是「线上跑的不是最新代码」。这个最容易被冤枉，也最容易证伪 —— 线上 /js/modules/{shell,cursor,effects,settings,reading,nav}.js 与本地 public/js/modules/*.js 过一遍同版本 terser 之后是逐字节相同（shell.js 两边都是 d4aad074ca27）；/css/index.css 也只是 clean-css 的等价改写（bold→700、0.2s→.2s、*::selection→::selection），规则级 diff 下来没有一条语义丢失。连缤纷云镜像 fomalhaut.s3.bitiful.net 都和 Vercel 逐字节一致。这条路走不通。

第二个是「标签页用久了会退化」——前几轮修过动画循环的生命周期，很容易往这上面靠。为了验证它，我在同一个 Chrome 里开了一个全新的标签页做对照：线上全新加载 85fps，本地 84fps，干净状态下两边没有差别，说明「线上天生慢」不成立。

中间还有一次差点把我带沟里的证据。任务管理器截图显示「本地的」标签页 0.2% CPU、「线上的」110.7% CPU，看起来板上钉钉。但把两张图放大对齐才发现：两行高亮行的进程 ID 都是 8408，那是同一个标签页的两次快照 —— 一次隐藏、一次可见。而「FPS:87 十分流畅」这个数字也不可信：source/js/modules/reading.js 的采样在 document.hidden 时会挂起，屏幕上是暂停前留下的陈旧读数（本地那行的标题「👀跑哪里去了~」，正是 source/js/modules/shell.js:191-205 在页面隐藏时才写的恶搞标题）。「同一时刻、同一条件」这两句话，得对数据本身也用一遍。

真正的分叉在 DevTools 的 Performance 里：线上单帧 75ms 里有 64ms 是「重新计算样式」，整条主线程被它填满；本地同一帧只有 26ms 渲染 + 26ms 绘制。样式重算的成本 = 被失效的元素数 × 需要匹配的规则数，既然 DOM 和 CSS 都一样，多出来的规则只可能来自浏览器侧。

于是一试就中：无痕窗口（默认禁用全部扩展）打开线上首页，和本地一样流畅；回到普通窗口单独关掉 AdGuard 广告拦截器，立刻恢复。

机制很朴素：广告拦截器的隐藏规则是按下发域名生成、注入成一张额外样式表的，而 localhost / 127.0.0.1 天然被排除在过滤范围外 —— 同一份代码，线上每帧要多匹配一大截规则，本地一条都不多。所以这不是站点 bug，只有装了广告拦截器又没放行本站的访客会遇到；对策是给本站放行，而不是长期关掉拦截器。

顺着这条线还揪出 themes/fomalhaut/source/sw.js 里的三个真缺陷，一并修了：

  • 缓存失效只认 index.html 的哈希，其余资源走 cache-first + 24 小时 TTL。如果某次发版只改了 JS/CSS 却忘了同步改 ?v= 缓存戳，URL 和 HTML 都不会变，回访者会继续跑旧代码最长 24 小时 —— 这正是「CI 绿了但线上还是旧代码」的成因。现在把文本资源（html/js/mjs/css/json/xml/txt/map/webmanifest/manifest/svg）的 TTL 压到 10 分钟，图片 / 字体 / 音视频仍按 24 小时，并把 CACHE_NAME 提到 ICDNCache-v3，老访客在 activate 时整体丢掉 v2 残片。
  • getFileType() 的白名单只列到 ttf，其余一律 text/plain。站内会走 SW 的自定义光标 source/assets/c*.cur、atom.xml / sitemap.xml / search.xml 都被猜错了类型，已补齐 cur/avif/bmp/apng/otf/eot/xml/txt/map/webmanifest/manifest/mp3/m4a/mp4/webm/pdf/wasm。
  • 线路探测把缓存撑大了：source/js/inject/ping-route.js 每次探测都用「站点自身域名 + 一个新的随机串」请求 /?__pr=xxx-N，在线上会被 SW 接住并走 HTML 分支 —— 改写回缤纷云、下载整份 index.html（约 98KB）、写进 ICDNCache。缓存键包含查询串，而随机串每次都不同，所以这些条目以后永远读不到，只是一直占地方；探测在页面加载、每次 pjax 跳转、以及每 5 分钟各来一轮，逛得越久堆得越多。现在带 __pr= 的请求只做「改写 + 回源」，不落地缓存 —— 量到的仍然是「本机 → 缤纷云」的往返，侧栏线路徽标的数字不变。

新增 tools/tests/sw-cache.test.cjs：纯 VM 跑 Service Worker 源码（caches / fetch / Response 全部打桩，不联网、不起服务），9 项断言覆盖域名白名单、回源到缤纷云、二次请求吃缓存、「js 11 分钟旧 → 触发一次后台校验 / 5 分钟新 → 不动 / webp 25 小时旧 → 才校验」的 TTL 分流，以及探测请求不写缓存、普通 HTML/JS 仍照常写缓存两条回归保护。备份与回滚说明在 bak/sw-cache-20261005/。

九十六、AI 助手吐字卡顿：不是 Markdown 慢，是每帧都在逼浏览器同步布局

面板里问一个长问题，字往外吐的时候，页脚那个一直开着的帧率面板从 90 掉到 60 出头，肉眼就是一顿一顿的。回答越长越明显，短问答看不出来。

先列三个嫌疑人：Markdown 解析（每个分片都拿累积的全文调一次 md()，看着就是 O(n²)）、气泡整块重建（每个分片都 innerHTML = ...）、滚动。最像元凶的是第一个，所以先去量它。

量法很土：把 esc() 和 md() 从 source/js/ai-chat.js 里按行号切出来，丢进 new Function() 里跑。之所以按行号切，是因为这个文件不缩进、函数内部的 } 也顶在第 0 列，用 indexOf('\n}') 找函数结尾会切错，自己写的括号配平扫描器又被文件里的正则和模板串搞乱了 —— 按行号切最稳。

真凶在分片循环里那三行：

innerHTML = ... 是整块重建（连里面的 .ai-cursor 光标动画都跟着重来）；scrollBottom() 里为了判断「用户是不是贴着底」，先读 scrollHeight - scrollTop - clientHeight，再写 scrollTop —— 读一下、写一下，每读一次都在逼浏览器立刻把布局算出来。写了个探针在真机上量三条 20 秒的流：28 秒里有 8.1 秒花在强制同步布局上（3816 次读取，平均每次 2.1ms），面板里 innerHTML 写了 955 次。

于是改了四处。

一是合并渲染。 分片只往 acc 里堆文本，DOM 提交交给 requestAnimationFrame，并且只保留最新的一次；另配一个 100ms 的定时器兜底 —— 页面切到后台时 rAF 会停摆，不兜底就会一直不刷新：

二是滚动只写不读。 用一个 stick 标记记住「是否跟随」：渲染时只写 scrollTop = 1e9（越界值浏览器会自己夹到最大值，不需要先读内容有多高），只在用户的 scroll 事件里读一次「是不是在底部」。副作用正好是我想要的：手动往上翻就不再跟随，滚回底部自动恢复。

三是只重建「尾巴」。 新增 tailCut()：从上次定稿的位置往后逐行扫，只在「代码围栏之外、不在有序列表中间、行内 ** 与 [] 成对」的行尾把之前的内容定稿 —— 已定稿的部分用 insertAdjacentHTML 一次性追加进去，每帧只重渲尾部那一小块。有序列表不能切，因为切开之后编号会从 1 重来；无序列表可以，两段列表之间只多一个会被 margin collapse 吃掉的空隙，而 finish() 收尾时本来就会整块重渲一次。切点的正确性在 Node 里验过：拿真实回答（2008 字）按 1 / 3 / 11 / 17 字四种分片步长喂前缀，逐前缀断言「拼接结果 === 整条重渲染」，48 处切点、最大尾块 111 字、0 处不一致。

四是让面板提前建好。 prewarm() 是幂等的，空闲时（requestIdleCallback，2.5 秒超时兜底）或鼠标移到按钮上时，先把面板 DOM 建出来并强制算一次布局 —— 首次点开那一下的长帧就是这么来的。

  • 先量化再动手。 最像元凶的那个 O(n²)，实测只占 195ms。

贡献日历不再是一套写死的绿

GitHub 贡献日历的十档颜色原来写死在 _config.yml 的 gitcalendar.color 里。问题是这个站的主题色可以换（美化面板里九个色块，外加一个「恢复默认设置」），日历却一直是那套绿 —— 换完主题色，全站都跟着走了，只有那块日历纹丝不动。

现在 source/js/gitcalendar.js 顶部多了一个 git_theme_palette()：读 :root 上的 --theme-color，用两条正则接住 rgb() / rgba() / #rgb / #rrggbb，再按 [0, .16, .28, .4, .52, .64, .76, .86, .94, 1] 这组透明度叠加出十档。第 0 档（没有提交的格子）固定是 rgba(128, 134, 140, .22)，偏中性的灰，白天夜里都合适；第 1~9 档是主题色由浅到深。用透明度叠加而不是 color-mix()，是因为前者在任何浏览器上都能算，后者要写 @supports 兜底。读不到主题色（值既不是 rgb 也不是 hex）就返回 null，调用方继续用配置里那套 —— 配置项从「唯一来源」退成了「兜底」。

配套的重画逻辑在 GitCalendarRefresh()：美化面板的 setColor() 里多调一句它，但它先比较「画布上那份用的是哪个主题色」和「现在 --theme-color 是什么」，一样就什么都不做。这一条很重要 —— 页面加载时那次 setColor 必然发生，此时首次渲染正在路上，插手就会撞车；「恢复默认设置」是先写 localStorage 再调 setColor，颜色其实没变，也会原地跳过。

顺手补了两个并发缺口。一个是「旧请求回来得比新的晚」：每次 GitCalendarInit 领一个递增的 git_init_seq，fetch 的 then / catch 里先对一次序号，自己不是最新就直接 return，别让旧数据盖住新画布。另一个是「重复初始化会叠出两份」：fetch 回来先 git_container.innerHTML = '' 再画。页面刚打开就连点两下主题色，两条路都不会再叠出两份日历了。

指针判定的两层缓存

小猫咪（source/js/modules/cursor.js）上一轮改成了读写分离，这一轮把「这个元素能不能点」的判定做得更细。

原来只有一层 pointerCache，缓存「目标 → 是不是可点」。但判定本身有两段成本：target.closest('a[href], button, …') 要走一遍祖先链，找不到语义控件时还得逐级 getComputedStyle 去认 cursor: pointer。鼠标在按钮和它内部的 <span> / <svg> 之间来回移动时，这一段会反复重算。

现在拆成两个 WeakMap：controlCache 缓存「元素 → 它属于哪个语义控件」，ancestorPointerCache 缓存「元素 → 祖先链上有没有 cursor: pointer」。同一轮 hover 里，子元素往返直接命中。两个细节：disabled 要实时读，不能跟着控件身份一起缓存 —— 按钮禁用了而缓存还说可点，光标就会一直顶着可点的样子；祖先链缓存只在该 hover 版本内有效，mouseover / mouseout / elementFromPoint 换目标都算新版本。

MutationObserver 也跟着做了分级。以前只要有一条和自己无关的变动，整轮缓存就重建；现在 pointerMutation() 给每条记录打分，0 完全忽略、1 只重查位置不清语义缓存、2 全量失效：

  • 0：光标自己的节点、猫咪气泡的 data-msg 属性、#fps 计数器上的 title；
  • 1：帧率面板里那几种「纯输出」的文字节点 —— 加了个 fpsOutputNode() 判定，只放过「属性只有一个 style、值是那几个已知颜色、子节点全是文本」的 span；
  • 2：其余一切，包括未知结构、重排，以及宽度会变的输出（宽度一变，鼠标底下的元素可能就换了）。

底线是「宁可多失效，不能漏失效」：能拿 0 和 1 豁免的，都是已经确认过的纯装饰输出，其余一律按 2 处理。一帧里 MutationObserver 可能投递好几批，所以 invalidatePointer() 不再当场重建缓存，只标脏，统一到 render() 里重建一次。回归脚本 tools/tests/cursor-effects.test.cjs 跟着从 4 个用例扩到三十来个（跑法仍是 node --test "tools/tests/*.test.cjs"），专门盯「该失效的失效、该命中的命中」。

窄屏那点横向溢出，一共两处

两处都只在手机 / 窄屏上出现，症状都是「页面被撑宽约 10px，手指一拖整页跟着横移」。

第一处是作者卡右上角的回形针（source/css/paperclip.css）。--clip-right 原来写死 -21px —— 桌面端卡片两侧余量足，探出 21px 正好是手账式的别针感；手机上卡片几乎与视口等宽，这 21px 就顶出屏幕了。改成 calc(-21px + max(0px, 23px - (100vw - 100%) / 2))：余量足时仍是 -21px，卡片接近满屏时逐步收回卡内。

第二处是时间线归档页（source/css/timeline-archive.css）。栅格第二列原来写 1fr，而 1fr 的最小尺寸是 min-content —— 页面上最长的不可断词是一串斜线清单（cur/avif/bmp/…/wasm，约 88 字符、单行 654px），它把整条轨道顶到 687px，卡片撑破 390px 的视口。改成 minmax(0, 1fr)、再给 .timeline-item-content 补 min-width: 0，轨道不再有 min-content 底线，长串交给卡片上已有的 overflow-wrap: break-word 断行。年表也一起改了，?v= 提到 20261011。

几处顺手

  • 设置面板的复选框：custom.css 里那句 transform: translateY(5px) 是更早「文字与开关同行、按基线对齐」时补的；后来外层 .opt 改成 flex 居中，这 5px 就把开关压到了文字中线下方，删掉。
  • 主题色那一行：两圈颜色之间的空隙本来没有可选文字，但点一下会落下编辑光标（会闪的那道竖杠）。给 .colorRow 补 user-select: none 与 caret-color: transparent。
  • 关于页第 5 层：技术栈里「结构化存储」原来写着托管 Twikoo 评论与 Ispeak 哔哔两份数据；哔哔那套已经不用了，只留评论。
  • 页脚的徽章：npmmirror 那枚换成源站去掉 shields.io 阴影的版本（浅底深字有阴影会显重影）；本地 source/assets/badge/ 下最后 4 枚 SVG（主题、npmmirror、摸鱼牌两张）删掉，摸鱼牌改回缤纷云的地址 —— 线上一直走那个桶，本地再留一份只是多一处要同步；顺手把安卓客户端的体积标注从 3.3MB 改成 8.6MB。
